# Windows Desktop 开发验证（2026-11-02）

后续改进：所选片段按原片时间顺序合并为单个 MP4，输出前后复验缓存并检查合并结果；使用合成缺片视频验证顺序与不覆盖。Windows 原生及 offscreen 后端各 130 项测试通过（后续变更需重新验证）。在同一组 16 项合成缓存上，单线程扫描 1.115 秒、四线程 0.416 秒；该结果不代表所有磁盘和缓存规模。缓存时间采用索引 StoreWithTime 的系统时间；无此记录时显示未知。界面检查见 [Windows GUI 视觉检查](windows-gui-audit.md)。

使用自制新旧 PBKDF2、Argon2id、scrypt 密钥封装、加密索引与 FFmpeg 测试视频验证普通缓存、流式分片、界面与命令行片段导出；源条目改变或校验失败时拒绝使用。Windows 的合成文件测试覆盖前四字节锁、稀疏文件分配、缓存路径外导出和 portable 自定义数据名、多账号目录选择及模拟运行进程的自动定位。索引的 32 字节 Store 布局另以 Windows MinGW 编译的 C++ 同字段结构核对。扫描复用数据库索引，但片段导出前后重新读取源索引和内容。没有读取本机 Telegram 真实缓存。

当前已知限制：Desktop 分片索引不能单独证明原片总长度。连续的未知长度缓存可以显式导出已缓存内容，文件名标记完整性未知，导出前后复验源并检查输出解码；有缺口或解码失败时尝试恢复片段。对缺失、损坏或无法辨别格式的分片仅忽略该分片，并提示未参与恢复。尚未用真实 Desktop 缓存验证具体客户端版本、文件锁定竞争和视频覆盖率；未完成人工视觉验收。临时目录需要支持稀疏文件，外部 FFmpeg/ffprobe 不随包提供。

Windows 上使用 `QT_QPA_PLATFORM=windows` 原生 Qt 平台插件运行 `tests/test_gui.py` 和 `tests/test_desktop_scan.py`，共 40 项通过。前者覆盖窗口、实际视频帧、筛选、导出与缺片面板；后者覆盖合成的 Desktop 扫描、预览、片段导出、本地密码及多组数据选择。另用中文路径的合成便携目录和导出目录完成两次导出，验证不覆盖、缓存未变及关闭后临时目录清理；损坏账户索引的测试确认其他结果和错误提示都保留。所有扫描均显式指向测试生成的目录；这属于自动化验证，不代表已进行人工视觉验收。

另以独立进程锁定合成 TDEF 分片的盐值区，验证其不可读时仍保留同一视频的可读头部、报告缺失分片；解除锁定后重新验证会检测到源状态变化。此测试不能代表真实客户端运行时的全部竞争情况。

合成加密记录还覆盖重复范围内容不一致：冲突的交集从所有副本排除，其余范围保留并标记受影响的分片。对于普通缓存，[Desktop 下载源码](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/storage/file_download.cpp)在原始长度未知时也可能不加 `partial:` 前缀，因此无前缀不能单独证明完整长度。

恢复片段在分析完成时记录内容哈希，导出时核对复制出的临时文件并重新解码；用另一段仍可解码的合成视频替换临时片段后，导出会拒绝该片段。原始缓存的复验仍独立执行。

Desktop 结果的名称、搜索和排序使用缓存键与实际缓存库路径；快照时间不作为原视频时间展示或参与最近修改排序。两组合成账户的同键视频验证了按账户路径筛选与详情显示。

补充：依据 [Telegram Desktop 流媒体缓存读写源码](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/media/streaming/media_streaming_reader.cpp)，头部记录后可包含另一张首分片表。合成加密缓存测试确认后表损坏时保留可解析的前表，并标记该记录有损坏；超过分片大小的连续记录会被拒绝。末尾连续记录的判别仍依赖外部原始长度，不能据此猜测完整性。

## v0.2.0 已发布版本

平台：macOS / Apple Silicon；Python 3.12、PySide6 / Qt 6.12.0，外部 FFmpeg。
